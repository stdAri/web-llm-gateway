# 01: Open the pipe — a local HTTP request reaches the real DeepSeek page and returns its answer

**What to build:** The thinnest complete path through both halves of the system. A local HTTP request carrying a line of text reaches a DeepSeek tab that the Developer User is already logged into in their own browser, the text is submitted into a real web conversation, and the answer DeepSeek generates comes back to the caller. This is the tracer bullet: it proves the daemon, the Bridge Protocol, the userscript Bridge, and a real Web Provider Adapter can work as one path before anything is built on top of it.

Scope is deliberately narrow. The caller is `curl`, not an Agent Client. The answer arrives complete rather than streamed. There is no model selection, no tool loop, and no queueing. The Bridge authenticates with a Bridge Pairing Token, since it cannot connect without one; the Gateway API Key belongs to ticket 02, where a real client first needs it.

Per ADR-0014, the daemon must learn the provider from what the Bridge announces at registration. Do not compile a provider list into the daemon.

**Blocked by:** None (can start immediately)

**Status:** done

- [x] A repository workspace exists with a test runner and a build that produces a single installable userscript artifact
- [x] The daemon binds to loopback only and refuses connections from other interfaces
- [x] A pairing command issues a Bridge Pairing Token, and the Bridge cannot connect without presenting a valid one
- [x] The Bridge registers an open DeepSeek tab and announces its provider identity to the daemon, which routes to it without any hardcoded provider list
- [x] A local HTTP request carrying a text prompt causes that text to be submitted into the real DeepSeek web conversation
- [x] The answer DeepSeek actually generated is returned to the caller, and the same exchange is visible in the tab
- [x] Recorded, redacted DeepSeek frames are captured and committed, and at least one Provider Adapter parser test runs against them in CI without credentials

## Comments

- 2026-09-02 — Implemented. Bun + TypeScript monorepo-lite: daemon (loopback HTTP + WebSocket BridgeHub + pairing token store), userscript Bridge (page-context fetch/XHR interception, React-aware composer set, tab registration + heartbeat), DeepSeek adapter as pure parser over recorded frames. End-to-end verified: mock Bridge registers a DeepSeek tab and answers a curl turn; LAN-interface connections refused. 11 tests pass, typecheck clean, single userscript artifact builds to `dist/bridge.user.js`.
- Note: the parser test uses synthetic redacted frames (fixtures/deepseek/completion-stream.json) since real DeepSeek frames require the live-site smoke (Surface three) to capture and redact; the fixture format is ready for those frames to be dropped in.
- 2026-09-02 — Two follow-up fixes found while preparing the first real browser run. (1) The generated artifact did not parse: `buildUserscript` declared `const CONFIG` and `bridgeRuntime()` re-declared it in the same scope, so Tampermonkey rejected the whole script with `Identifier 'CONFIG' has already been declared`. The build now emits one binding and `node --check dist/bridge.user.js` guards it. (2) The Bridge Pairing Token was baked in at build time, which put a secret in the artifact published at `@updateURL` and meant every online update overwrote the pairing. Pairing is now the one-time runtime step spec user story 5 asks for: the token is entered once via `window.prompt`, kept in `GM_setValue` storage (which survives script updates), re-promptable through the `Pair with Gateway Node...` menu command, and cleared automatically when the hub closes with 4401. `BRIDGE_PAIRING_TOKEN` is gone from the build.
- 2026-09-02 — Added an on-page status badge to the Bridge. Pairing and connection state were only observable from the browser console or the daemon's `GET /`, so a Developer User had no way to tell whether the Bridge was paired. The badge sits bottom-right in the Web Product tab and reports `not paired` / `connecting` / `connected` / `running turn` / `token rejected` / `daemon offline`; clicking it pairs when unpaired or rejected, and collapses to a dot otherwise. New `tests/bridge-artifact.test.ts` runs the built artifact against a stub DOM and drives the whole handshake, which is the regression test the duplicate-`const CONFIG` breakage should have had.
- 2026-09-02 — First real browser run failed, and the acceptance criterion "the answer DeepSeek actually generated is returned to the caller" was never truly met. The artifact called `parseDeepSeekFrame` and `assembleDeepSeekAnswer` as bare identifiers but never defined them: `buildUserscript` is string templating, not a bundler, and a userscript has no module loader, so the imports resolved to nothing. The artifact parsed cleanly (`node --check` passes on it), then threw ReferenceError mid-turn — in `poll`, *after* `clearInterval(timer)`, so no `turn.result` was ever sent and `curl` hung until the daemon's 300s turn timeout. The adapter's transpiled source is now inlined into the artifact, guarded by a check that the adapter has not gained imports of its own. `tests/bridge-artifact.test.ts` now drives a full turn against the recorded fixture frames and asserts the assembled answer is published, plus the no-frames path that must still answer the daemon rather than strand it.
- 2026-09-02 — Root cause of the empty answers, found by driving the live page over AppleScript rather than guessing: `findSendButton` matched on `aria-label`, and DeepSeek's send control is an icon-only `div[role="button"]` with no aria-label and no text. On the live page 117 candidates matched the element query and **zero** matched the label test, so the prompt was typed into the composer and never submitted. Verified on the page that `div[role="button"].ds-button--primary.ds-button--filled` matches exactly one element, and that it carries `ds-button--disabled` while the composer is empty and drops that class once filled — which also proves the existing React-aware value setter works. Selectors now live in the DeepSeek adapter (composer, send control, disabled marker) rather than in the generic Bridge, and a disabled control is refused instead of clicked.
- 2026-09-02 — Parser rewritten against the real protocol, guided by the reference implementation: DeepSeek's stream is stateful — bare `{v: "…"}` frames carry no type and inherit it from the preceding fragment frame, and content-less frames (e.g. an `elapsed_secs` SET) must reset the sticky bucket so trailing bare frames are not glued onto a finished fragment. The old stateless per-frame parser was only ever validated by a synthetic fixture encoding an OpenAI-style protocol DeepSeek does not speak, which is why 92 real frames parsed to 0 while tests stayed green. The fixture is now 56 real frames captured from a live page (checked before commit: no tokens, cookies, or email), parsed by stateful assembly with a `response/status: FINISHED` completion signal so turns return in seconds instead of waiting out the timeout. First genuinely live end-to-end pass: `POST /v1/turn` returned "中国的首都是北京，答案编号73。" in 3.1s from the real page (diagnostics: 115 raw frames parsed, composer and send control found). 48 tests pass, typecheck clean.
- 2026-09-02 — Live verification complete. The Developer User confirmed both exchanges (markers 73 and 42) are visible in the DeepSeek tab, satisfying the last acceptance criterion against the real site. No caveat remains on this ticket.
